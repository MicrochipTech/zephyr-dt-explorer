## Findings

### Tool bug 1: SG41, the port overlay is not accepted by Zephyr (all four labs, verify rc 1)
The SAME54 Xplained Pro uses `&sercom4` as SPI (EXT1). The board file of `pic32cx_sg41_cult` already uses `sercom4` as console UART
(`zephyr,console = &sercom4`, `current-speed = <115200>`, `pinctrl-0 = <&sercom4_uart_default>`). The port overlay sets the compatible of
`&sercom4` to `microchip,sercom-g1-spi`, plus `dipo`, `dopo` and pinctrl; the board's `current-speed` stays on the node and Zephyr rejects it:

```text
devicetree error: 'current-speed' appears in /soc/sercom@43000000 in .../build/zephyr/zephyr.dts.pre, but is not declared in 'properties:' in C:\Masters\zephyr-main\zephyr\dts\bindings\spi\microchip,sercom-g1-spi.yaml
```
Report section 6 (fast check) shows the same error, so the tool sees it, but section 1 lists the node as `[emitted]` without a hint. Expected: the port
deletes (`/delete-property/ current-speed;`) or at least reports properties that the target board set on the node and the new binding does not
declare. The chosen entries `zephyr,console`/`zephyr,shell-uart = &sercom4` of the board also stay on the node that is now SPI; the overlay does not
move the console. The same problem arises for any compatible swap on a node that the target board configures differently.

### Tool bug 2: SG61, the sercom4 SPI is silently not ported while verify is green
On the SG61 the pads PB26-PB29 are `INTERNAL` in the ATDF; the formatter cannot render `PB27D_SERCOM4_PAD0` ("MOSI: pad PB27 is not a signal of
SERCOM4", node status `[error]`, note "cannot render"). `&sercom4` is then missing from the overlay (the board's own UART stays), so verify
passes (rc 0) although the labs' SPI is not ported. Dropping it is right for the pins, but: (a) the verify result reads green and the only red marks are
section 1 `[error]` and section 4; (b) the wording "pad PB27 is not a signal of SERCOM4" is misleading: it is a SERCOM4 signal on SAME54 and SG41, on SG61
the pad is not on the package; section 4 prints this line and three "not on package" lines for the same pads (4 lines for 3 pads); (c) there is no
suggestion where the SPI could go.

### SG61 pin report check (step 4)
Section 4 of every lab/SG61 report lists exactly PB26, PB27 and PB29 ("not on package TQFP128 of the target device PIC32CX1025SG61128"), used by `&sercom4`.
PB28 and PC04 are not used by the labs and are correctly absent. SG41: section 4 is `none` for all four labs. This matches, with one deviation from the
card text "none expected for the labs": all four labs hit it, because `same54_xpro.dts` itself enables `&sercom4` as SPI on PB26/PB27/PB29 (EXT1),
independent of the lab code. Section 7 (connector roles) adds for both CUlt boards: EXT1 pin 18 (SCK, PB26 on the Xplained Pro) "not available ... (net
NetJ602_18 does not reach the SoC)", PB27 -> PB24, PB29 -> PC25; that is board information on SG41, where section 4 stays `none` (the pad exists on the chip).

### Further observations (not blocking)
* SG61 fast check, `error: pin_conflict`: PD08 and PD09 are used by `sercom6` (the board's `i2c0: &sercom6`) and by the lab's `sercom7` I2C (ported with PD08/PD09). Zephyr does
  not check pin conflicts, so verify passes; at run time the two SERCOMs would fight over the pads. Visible in all four SG61 reports. The SG41 reports cannot show it (the
  fast check ends at the edtlib error of bug 1).
* Section 7 maps the lab I2C (SDA PD08, SCL PD09 on EXT2 of the Xplained Pro) to PD09/PD08 on the CUlt (swapped), while the ported overlay keeps PD08C/PD09C unchanged.
* Lab3: `DT_ALIAS(sercom3)` in `src/main.c:32` is `[missing]` on both boards (section 3 suggests `aliases { sercom3 = &sercom3; }`; it is not in the overlay).
* Target cmake-only builds of the unmodified labs on `main` (before porting): rc 0 for all 8, about 82-86 s each with 8 running in parallel (`ZEPHYR_EXTRA_MODULES` resolves
  inside the RTOS4 workspace because the apps are used in place). No Kconfig/module incompatibility of the apps with 4.5.0-rc1 appeared; no app/workspace limitation found.
* First attempt (tool at `9998b9e`): all 8 `port_build` calls raised `FormatterError: cannot derive a pinctrl header name from SoC 'pic32cx1025sg41128'` (and `...sg61128`),
  because `find_header` knew only SAME5x. Fixed by the builder in `354710c`; all results below use that commit. Traceback of the first attempt (lab1 / SG61):
