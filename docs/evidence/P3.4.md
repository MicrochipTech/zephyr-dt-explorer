## How the overlay is checked

1. `build_info.yml` of the build supplies what Zephyr used: devicetree `files`, `include-dirs`, `bindings-dirs`; CMakeCache supplies the compiler (`CMAKE_DTS_PREPROCESSOR` or `CMAKE_C_COMPILER`), `DTS_EXTRA_CPPFLAGS`, `ZEPHYR_BASE`.
2. The preprocessor call is the one of `zephyr_dt_preprocess`: `gcc -x assembler-with-cpp -nostdinc -isystem <dir>... -include <board.dts> -include <app overlay> -include <draft overlay> -undef -D__DTS__ -E -o draft.dts.pre zephyr/misc/empty_file.c` (cwd = application dir). The draft is the last `-include`, so its macros resolve against the build's own headers. The draft path is passed with forward slashes, so cpp's line markers keep it recognisable.
3. `edtlib.EDT(draft.dts.pre, bindings-dirs, default_prop_types=True, infer_binding_for_paths=[/zephyr,user, /cpus], werror=False)`. `EDTError`/`DTError` become an error finding (`missing_property` when a binding's required property is absent, with property, node and binding name).
4. `BuildModel.from_edt(edt, build, origins)` (new classmethod in core/build.py; the constructor is unchanged) feeds `core.pins.used_pins`. The pinmux source positions come from dtlib (`Property.filename/lineno`, which cpp's line markers keep pointing into the original files and the draft), so the existing macro-name decoding works on the merged tree.
5. Nodes touched by the overlay = nodes with a property whose source file is the draft, plus nodes whose pinctrl state nodes have one. A pad used by two or more nodes is an `error` when a touched node takes part; otherwise `info` (`pin_conflict_existing`, here the LED/TCC0 conflict on PC18 that the build already has). A touched node whose signals of one instance have no group in common gets the provider's `shared_group` constraint text as `warning`.
6. Speed: edtlib opens each of the ~3400 binding files on every run (2-3 s on this machine). `validate` shadows `open` inside the edtlib module with a cache keyed by path and mtime, so only the first call pays.
