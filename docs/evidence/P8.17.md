## What changed (core/port_report.py)
* A node that is a `conflict` (reasons a, b or c of P6.3) is no longer only judged by `_conflict_suggestion` (text). `_plan_remap` does the work and `port_build` acts on it:
  1. each source pad -> the source connector pin it sits on -> the pad at the same pin of the same connector (name and type) on the target board. One connector for all roles (the connector that maps most roles wins). A role without a pad there (untraced net, not on the package) makes the node `no remap`.
  2. instances of the target device model whose provider signals offer exactly those target pads (one signal per pad), where the recipe's `valid_assignments(class)` has an assignment with exactly those roles on exactly those pad roles, and where `derived_props` accepts it.
  3. the instance must be free: its register base has no enabled node in the target build; none of the target pads is used by any node of the target build; neither pads nor base belong to another node that this port carries over on its own instance (pre-pass over all draft nodes) or to a node remapped earlier in the same run.
  4. the first fitting instance (device order) is taken; the node of that instance in the target devicetree is run through the same conflict check (`_target_conflicts`) with the new pads. If it still conflicts, the node stays `conflict` and a line `remap to X rejected: ...` says why.
* Result `remapped` (section 1): the normal emission path with the target instance's node, the new pads, `dipo`/`dopo`/`rxpo`/`txpo` recomputed by the recipe from the *target* device model signals (not the source's), lines `remapped: <class> <src instance> -> <target instance> (&src -> &tgt); the connector pins stay the same (<connector>)`, `remap <ROLE>: <src pad> (<connector> pin <n>) -> <target pad>`, `remap because: <conflict reason>`.
* Consequences: chosen entries and aliases of the node move to the new label unless the target board already defines that chosen/alias (then it stays and a note says so); `note: code that uses DT_NODELABEL(<src>) must use DT_NODELABEL(<tgt>)`; section 3 reports `DT_NODELABEL(<src>)` as `[remapped]` with suggestion `DT_NODELABEL(<tgt>)` and an alias entry `<src> = &<tgt>;` in the overlay; app overlay text that refers to `&<src>` is rewritten to `&<tgt>`; the clock rule note of the source node is not used for the new instance (it would name the wrong instance), a note asks to check the clock controller of the target board.
* No remap: the conflict stays, the suggestion line now ends in `no remap: <why>` and names instances that muxed the pads but could not be used (`not usable: SERCOM6 (enabled as &sercom6)`, `pad PB24 in use`). Differences to P6.3 for the suggestion text: an instance that is enabled in the target is no longer offered (P6.3 offered it when it was the node's own target), pads used by other nodes of this port are named.
* Tests: tests/test_port_report.py, 2 existing tests adapted (suggestion text), 9 new tests. UI (ui/port.py) counts only `conflict`; a `remapped` node is therefore not in that count (outside this card's write scope).
* Vendor-term grep (`atdf|ioset|mchp_packs|sercom|atmel|microchip|samd|same5`, case-insensitive, lines in `dt_explorer/core/*.py` + `dt_explorer/ui/*.py`): master 32, now 32; `core/port_report.py`: 5 before, 5 after.
