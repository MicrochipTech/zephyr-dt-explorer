## 0. Free resources on the board (core API, `ConfigSession`)

The CUlt board already uses: SERCOM4 = UART console (PB12/PB13), SERCOM0 = SPI (PB24/PC25/PB25), SERCOM6 = I2C `i2c0` (PD09 = SDA, PD08 =
SCL, with `eeprom@56`, `eeprom@5e`), **GMAC + MDIO + PHY already enabled** (RMII PA12..PA19, PC20; MDC/MDIO PC22/PC23). The
mikroBUS socket (board YAML, J900/J901): MOSI PB24, MISO PC25, RX PC13, TX PC12, SCL PD08, SDA PD09, SCK without a pad.

Decisions: the UART goes to **SERCOM7**: it is unused and muxes exactly the mikroBUS UART pads (PC12 = PAD0, PC13 = PAD1, mux C;

already uses for its I2C, so the sensor is a **child of the board's existing bus** (realistic: the mikroBUS I2C is shared).

**New vs already there:** nothing is new in hardware terms. The board already enables `&gmac` (`microchip,gmac-g1-eth`), `&mdio` and the
PHY `ethernet-phy@0` on exactly these pads (RMII PA12..PA19/PC20, MDC/MDIO PC22/PC23: the tool took MDC/MDIO from the current build,

**Kconfig lines** (`NETWORKING`, `NET_L2_ETHERNET`, `ETH_DRIVER`, `ETH_MCHP_GMAC_G1`, `MDIO_MCHP_GMAC_G1`): the board's
defconfig enables the driver, a blinky's `prj.conf` does not enable the network stack. See bug 1 for the line that should not be there.

## Tool bugs found (for the builder; product code not changed)

1. **`CONFIG_NET_TEST=y` is suggested for the PHY and switches Ethernet off.** `ConfigSession.kconfig()` returns for the
   compatible `ethernet-phy` (source `kconfiglib`, `core/kconfig_suggest.py`) the set `{ETH_DRIVER, ETH_PHY_DRIVER, NETWORKING,
   NET_TEST, PHY_GENERIC_MII}`. `NET_TEST` ("Network Testing", `subsys/net/ip/Kconfig:726`) is a symbol that `ETH_DRIVER` depends on
   **negatively** (`menuconfig ETH_DRIVER` has `depends on NETWORKING` and `depends on !NET_TEST`; Kconfig reports "unsatisfied dependencies:
   (!NET_TEST) (=n)"). Cause: `derive()` in `core/kconfig_suggest.py` climbs the `depends on` chain with `dep_syms(expr)`, which uses
   `kconfiglib.expr_items()`; that returns every symbol of the expression, also those under a `!`, so `NET_TEST` is collected as a "parent"
   and suggested as `=y`. Effect: the Draft tab Kconfig panel, `boards/<board>.conf` and the `prj.conf` block all contain
   `CONFIG_NET_TEST=y`; with it `ETH_DRIVER`, `ETH_MCHP_GMAC_G1`, `ETH_PHY_DRIVER`, `PHY_GENERIC_MII`, `MDIO_MCHP_GMAC_G1` are silently `n`
   (five Kconfig warnings, not errors), and the link fails with `undefined reference to __device_dts_ord_92` (the generated `dtx_phy.c` needs the
   PHY device). The draft check (0 errors) did not notice; Verify was not run in this scenario (it only configures; the Kconfig warnings are not
   errors for it either). Fix idea: walk the expression and skip symbols under `Not` (kconfiglib `expr_value`/ the AST tuple `(NOT, sym)`), plus a
   test with the compatible `ethernet-phy`.
2. **UART draft without `current-speed` compiles in dtc but not in C.** The "Configure..." dialog for a UART shows `current-speed` as an
   optional empty field (no default, no required marker). `microchip,sercom-g1-uart` reads `DT_INST_PROP(current_speed)` unconditionally, so
   the build fails: `'DT_N_S_soc_S_sercom_43000c00_P_current_speed' undeclared`. The draft check (0 errors) and Verify (cmake only) do not see it. Fix idea: a
   default (115200) or a "required by the driver" note for this compatible (recipe knowledge), or at least a warning when a UART node has no `current-speed`.
3. **Second Apply after a first Apply that created the files duplicates the draft.** A first Apply of a NEW file writes the plain draft
   **without** the `dt_explorer draft begin/end` markers (P8.13b only marks blocks it appends). When the draft changes and Apply is run again,
   the plan says `EXISTS ... Default: APPEND`, diffs "existing + draft block" and appends a *second complete copy* of every node after the
   unmarked first one (`phase2.out`: `@@ -106,3 +106,115 @@`; the file went from 109 to 220 lines, copy kept as `overlay_duplicated.txt` in `%TEMP%\p819`).
   dtc tolerated it here (identical labels and nodes merge), but any changed value would now be set twice and the old unmarked copy never
   gets updated. Fix idea: always write the markers, also for a NEW file, so that re-applying replaces the block; or detect that the existing file already
   contains the draft's nodes. (The conf file behaved correctly: "14 line(s) already in the file were left out", `skipped`.)

Not a tool bug but worth a hint in the Apply result: the "Next: west build -b ..." line is wrong for a build folder that was configured
before the overlay existed (here the cmake-only build the tool itself creates, "New build..."): Zephyr then ignores the new
`boards/*.overlay` and conf (cached lookup) and the build fails with `node bme280_76 is not enabled`; `west build -p always` is needed.
P8.13's evidence used `-p always` for the same reason.

## Surprising

* **`dtx_devices/` contains modules for the PHY and the two board EEPROMs** (`dtx_phy`, `dtx_eeprom`, `dtx_eeprom_mac`) because the lifted
  `&sercom6` / MDIO draft nodes carry them as children; only `dtx_bme280_76` was asked for. They link and `dtx_devices_init()` checks them as well
  (harmless, but the user gets code for devices the app did not add; the plan says "nvmem-layout has no node label: left out"). The eeprom
  modules got `sensor` as their kind ("sensor, atmel,at24"): the kind detection treats an EEPROM as a sensor.
* The I2C draft re-emits the board's `&sercom6` with `clock-frequency = <400000>` (the board writes `I2C_BITRATE_FAST`) and the two EEPROM children as plain text;
  it works (same values) but it is a copy of board content in the app overlay.
* The conf lines are written twice on purpose of the two paths: `boards/pic32cx_sg41_cult.conf` (Apply) and the `prj.conf` block (Generate code)
  carry the same 13 lines; Kconfig takes both without complaint.
* The test sensor will not answer on the CUlt without a real BME280 on the mikroBUS I2C: `dtx_devices_init()` would then return -ENODEV for the
  sensor at run time. Only the link was checked.
