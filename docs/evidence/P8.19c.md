```c
/* P8.19c acceptance: test main.c (not generated by dt_explorer). Uses the generated dtx_devices module. */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#include "dtx_devices.h"

int main(void)
{
	struct dtx_bme280_76_data d;
	int rc = dtx_devices_init();

	printk("dtx_devices_init() = %d\n", rc);
	for (;;) {
		if (dtx_bme280_76_read(&d) == 0) {
			printk("T=%d.%06d C  P=%d.%06d kPa  H=%d.%06d %%\n",
			       d.ambient_temp.val1, d.ambient_temp.val2,
			       d.press.val1, d.press.val2, d.humidity.val1, d.humidity.val2);
		}
		k_sleep(K_SECONDS(1));
	}
	return 0;
}
```

## Remaining findings (none breaks the build; product code not changed)

1. **GMAC + PHY via the recipe leave no trace in the overlay.** The recipe draft is identical to what the board already enables, so the overlay and the
   Draft snippet show nothing for GMAC/MDIO/PHY (correct for the build), and the only visible effect is the Kconfig lines. The PHY is a board node, so it gets no
   module in `dtx_devices/` either. This follows the P8.19b rules (items 5 and 6). Suggestion: a note in the Draft tab ("unchanged from the board") so the user sees why nothing is emitted.
2. **Kconfig suggestions still include `CONFIG_EEPROM=y` and `CONFIG_EEPROM_AT24=y`** although no EEPROM was added: the lifted `&sercom6` draft node still carries
   the board's EEPROM children for the Kconfig derivation (the overlay and codegen skip them since P8.19b). Harmless here (the board enables them anyway), but the board conf /
   `prj.conf` list symbols for devices the app did not add.
3. **The order of the suggested Kconfig lines is not stable between runs** (`CONFIG_SERIAL`/`CONFIG_I2C` swapped between the first and the second
   Apply for an otherwise identical set). Effect: a cosmetic diff in the conf/prj.conf plan ("-CONFIG_I2C=y / +CONFIG_I2C=y"). Sort the lines or make the derivation order deterministic.
