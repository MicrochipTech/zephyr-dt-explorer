## Findings

- **Same PCB.** The SG61 CAD folder `PIC32CX_SGxx_CULT_R5_CAD` is byte-identical to the SG41 one (59 of 59 shared
  files). The importer therefore reads the same `PIC32CX SG_CUltra_R5.PcbDoc`, only the device model differs
  (`PIC32CX1025SG61128.atdf`).
- **BOM evidence for the populated MCU.** `Assembly/02-00576-R5_BOM.xls` (read with `xlrd` 2.0.2; already installed),
  sheet "BOM Report": title "PIC32CX SG61 CURIOSITY ULTRA", part number EV09H35A, revision 5.0, PCB number 04-11671.
  Row for U401: `MCHP MCU 32-BIT 100MHz 1MB 256KB PIC32CX1025SG61128-E/XCB TQFP-128wEPAD`. Recorded in the YAML
  (`source.bom`, `mcu.part`). The pick-and-place file lists U401 as `TQFP-128_14x14`, top layer.
  The sheet "Project Information" still carries the R3 project file name (`PIC32CX SG_CUltra_R3.PrjPCB`), a
  stale text in the BOM tool output; the BOM title and revision field say SG61 / 5.0.
- **ATDF side.** In the SG61 ATDF the TQFP128 pinout maps positions 27 and 102-105 to pad `NC`, where the SG41 maps
  them to PC04, PB26, PB27, PB28, PB29. PB26-PB29/PC04 exist only as `type="INTERNAL_n"` pins (not on the package).
  (Position 5 is `NC` on both devices.)
- **Result for the connectors: no connector pin is affected.** On this PCB the U401 pads at positions 27, 102, 103,
  104, 105 have no net at all (probe below), and no net on the board is named PB26-PB29/PC04. So the SG61 YAML has
  zero pins with `available: false`, and EXT1/EXT2 are identical to the SG41 YAML (0 of 40 pins differ).
- **CONFIGURATOR.md check.** The statement "EXT1 SPI uses PB26-PB29" is true for the **SAME54 Xplained Pro**
  (J401 pins 15-18, see the Xpro table in P7.3), not for the SG41/SG61 Curiosity Ultra: there EXT1 SPI is
  PC24 (SS_A), PB24 (MOSI), PC25 (MISO), SCK untraced (`NetJ602_18`). The SG61 report conflict list for a SAME54
  project therefore comes from the SoC pin check (P6.2), not from the Curiosity Ultra connector map.

## Pipeline change (minimal)

`dt_explorer/importers/pipeline.py`:
- A MCU pad number whose package position is `NC` in the device model's package (the ATDF provider output for the
  chosen SoC) is a pad that exists on the PCB footprint but not on this SoC. The tracer no longer treats it as a
  normal pad: `Trace.unavailable` collects the footprint positions.
- A connector pin that reaches only such positions gets `available: false`, `pad: null` and `unavailable_reason`
  in the YAML, and a report line `... not available on this MCU`. It is not listed under GAPS (not a tracing failure).
  Pins of boards without NC positions get no new keys, so the SAME54 and SG41 YAMLs are unchanged.
- One report line always lists the NC positions of the package (`NC positions of TQFP128 on <SoC> ...`).
- Optional `mcu_part` / `bom_evidence` arguments (CLI `--mcu-part`, `--bom-evidence`) write `mcu.part` and
  `source.bom`.
