## What was built (`dt_explorer/core/port_report.py`)

`_carry_app_nodes` runs inside `port_build` after the covered nodes:

* Source text: every overlay file that contributed to the source devicetree (origin kind `overlay`) is parsed (comments and
  strings masked, braces matched); items are top-level children of `/ { }`, children of `&label { }` / `&{/path} { }`
  blocks, and properties of existing nodes. The text of an item is copied as written (macros untouched, one tab of indentation
  re-applied) under `/* carried from <overlay>:<line> */`, wrapped in `/ { }`, `&label { }` or `&{/path} { }`.
* Skipped silently (a translation or the port's own entries do it): properties of a covered node, aliases/chosen entries that
  point at a covered node, pin states that a covered node uses.
* Not carried, with reason in the new report section `5b`: the node references a label/path that is neither in the target
  devicetree nor defined by other carried text (fixpoint, so a chain reports the root cause); the bus parent is covered but not
  `emitted`/`identical` (not ported and enabled); parent missing or disabled in the target; label or path already in the target;
  pin state that no ported node uses; unsupported statements (`/delete-node/`, ...); an `#include` that does not resolve in the
  target workspace (reported, the carried text may need it).
* Carried labels count as resolved for `DT_NODELABEL(...)` references in `src/`; nodes handled here leave section 5.
* Core stays generic: the grep below shows no new vendor hits.
